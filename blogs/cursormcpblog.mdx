# Debugging Kubernetes with Cursor and the Odigos MCP: From Opaque 409s to a Verified Fix

Kubernetes incidents do not always begin with a crashing pod or an obvious exception.

Sometimes every workload is running, telemetry is flowing, and the application still is not working correctly.

That was the situation with **OdiShop**, a small production-like checkout application I deployed on Amazon EKS. Some checkout requests succeeded, while others returned an opaque HTTP `409` response:

```json
{"error":"fulfillment_rejected"}
```

There was no stack trace in the response, no failing downstream request, and no obvious Kubernetes condition explaining the problem.

Rather than opening Jaeger and manually clicking through traces as my primary workflow, I started in Cursor.

Cursor used the [**Odigos MCP**](https://docs.odigos.io/enterprise/mcp/overview) to inspect the cluster, verify instrumentation, read source conditions, understand the service map, enable profiling, and create instrumentation rules. When trace-level evidence was needed, Cursor queried Jaeger’s API through a local port-forward.

By the end, I went from an unexplained checkout rejection to the exact business decision causing it, without adding temporary logging or redeploying the application for each instrumentation change thanks to Odigos.

# The application: OdiShop

OdiShop is a small polyglot checkout application running on EKS.

It contains four application services:

- `api-gateway` — Node.js
- `order-service` — Java and Spring
- `inventory-service` — Go
- `payment-service` — Python

# Act 1: Is my OdiShop app healthy?

I started with a deliberately broad prompt.

> Is my OdiShop app healthy? Check the Kubernetes workloads, Odigos instrumentation status, telemetry flow, and any obvious application errors. Do not make any changes yet.

Cursor used the Odigos MCP to inspect the application and its instrumentation state.

At first, everything looked healthy:

- All four application service pods were running.
- Odigos had successfully instrumented each service.
- The uninstrumented `loadgen` pod was expected.
- Telemetry was flowing to Jaeger.
- There were no source conditions indicating a failed instrumentation attachment.
- The services appeared in the application topology.

From a Kubernetes and observability perspective, the environment looked fine.

But pod health is not the same as application health.

Cursor also reviewed recent checkout activity through the Jaeger API. That showed an elevated number of HTTP `409` responses on the checkout path, with the problem concentrating around `order-service`.

This gave me the first important finding:

```text
Kubernetes: healthy
Odigos instrumentation: healthy
OdiShop checkout flow: unhealthy
```

If I had only checked pod status and telemetry flow, I could easily have missed the actual user-facing failure.

# Act 2: Which service is returning the error?

Now that I knew checkouts were failing, I asked Cursor to locate the first meaningful failure in the trace.

> Find failed checkout traces and compare them with successful checkouts. Identify which service returns the error and show which downstream services were called.

Cursor queried Jaeger through its API and reconstructed the request path.

The failed traces showed:

- `api-gateway` received the checkout request.
- `api-gateway` called `order-service`.
- `order-service` returned HTTP `409`.
- `inventory-service` received `GET /stock` and returned HTTP `200`.
- `payment-service` was missing from the failed trace.

Successful checkouts followed the complete path:

```text
api-gateway
    │
    ▼
order-service
    │
    ├── inventory-service
    │
    └── payment-service
```

Failed checkouts stopped after inventory:

```text
api-gateway
    │
    ▼
order-service
    │
    └── inventory-service
```

That ruled out several possible causes.

Inventory was not returning an HTTP error.

Payment was not rejecting the transaction.

Payment was never called at all.

The decision to reject the checkout was happening inside `order-service`, after the inventory request completed and before the payment request began.

The problem was that the existing spans did not explain that decision.

The only response body was still:

```json
{"error":"fulfillment_rejected"}
```

The trace showed where execution stopped, but not why.

## A real library-coverage lesson

I encountered a separate tracing issue while building the demo.

The first version of `order-service` used:

```java
java.net.http.HttpClient
```

In this particular Odigos Java eBPF setup, that client was not covered for the outbound context propagation I needed. Inventory and payment generated their own spans, but they did not appear as connected children of the order trace.

I switched the application to Spring’s `RestClient`, and the downstream inventory and payment spans became part of the same distributed trace.

This was not the cause of the checkout failure, but it was an important reminder.

When a trace breaks at a service boundary, the first question should not always be:

```text
What is wrong with the downstream service?
```

Sometimes the real issue is library coverage or context propagation.

# Act 3: Dynamically enriching the traces

At this point, I knew the rejection happened inside the Java order service.

I still did not know which request characteristic triggered it.

The checkout request contained context that was not included in the default spans, including a fulfillment header and request body.

Rather than adding temporary application logs and rebuilding two services, I asked Cursor to create instrumentation rules through the Odigos MCP.

> Add instrumentation rules on `api-gateway` and `order-service` for the checkout path. Collect the `X-Fulfillment-Region` header and the HTTP request body, then compare new successful and failed traces.

Cursor created two types of rules:

- Header collection for `X-Fulfillment-Region`
- HTTP request-body collection

The rules were applied to the running services.

There was no application code change and no deployment required for the instrumentation update.

After generating another round of checkout traffic, the new traces included the missing request context.

A clear pattern appeared:

- Requests with `X-Fulfillment-Region: eu-west` returned HTTP `409`.
- Requests with `X-Fulfillment-Region: us-east` returned HTTP `200`.
- The captured request bodies showed the same fulfillment selection.
- Inventory still returned HTTP `200` in both cases.
- Payment appeared only on the successful path.

The problem was now reproducible.

```text
us-east checkout
    → inventory succeeds
    → payment runs
    → checkout succeeds

eu-west checkout
    → inventory succeeds
    → payment never runs
    → checkout returns 409
```

The dynamic rules told me which requests failed, but they still did not expose the business reason.

The HTTP spans only showed the service boundary.

The decision was happening deeper inside the Java application.

For a production deployment, I would keep payload and header collection narrowly scoped and review the captured fields for sensitive data. In this demo, the rules were temporary diagnostic instrumentation.

# Act 4: Profile the Java service

Since the order service was returning an intentional business response rather than throwing an exception, I asked Cursor to profile the process.

> Enable source profiling on `order-service`. Focus on application-owned code associated with the checkout path and identify any hot business functions.

Cursor called `enable_source_profiling` through the Odigos MCP.

The resulting profile showed a hot application function:

```text
FulfillmentGate.burnCpu
```

The surrounding source path pointed back to:

```text
FulfillmentGate.assessPipelineCoherence
```

This did not prove the function was broken.

A hot function is not automatically a bad function.

Profiling simply narrowed the investigation from the entire Spring service to one specific business-logic path.

Instead of searching through every controller, client, validation method, and fulfillment class, I now had a strong candidate for deeper instrumentation.

# Act 5: Instrument the business decision

The existing trace told me that inventory succeeded and payment never ran.

Profiling told me which application function owned the relevant execution path.

The next step was to capture the input and output of that function.

> Add custom Java instrumentation for `com.odishop.order.fulfillment.FulfillmentGate.assessPipelineCoherence`. Capture the first argument and the return value, then inspect the method span from a failed checkout.

Cursor called `add_custom_instrumentation` through the Odigos MCP.

The custom instrumentation was applied without modifying the application code or redeploying `order-service`.

The next failed trace contained a span for:

```text
FulfillmentGate.assessPipelineCoherence
```

The method argument exposed the request being evaluated:

```text
arg.0:
CoherenceRequest{
  region=eu-west,
  replicaSkewMs=47,
  warehouse=<selected warehouse>
}
```

The return value exposed the decision:

```text
return.value:
CoherenceDecision{
  allowed=false,
  reason=COHERENCE_FAIL: skew_exceeded skew=47 threshold=10
}
```

That made the root cause clear.

Inside `FulfillmentGate`, the application used a hardcoded threshold:

```java
MAX_REPLICA_SKEW_MS = 10
```

The `assessPipelineCoherence` method rejected the checkout whenever inventory reported a replica skew greater than `10 ms`.

For `us-east`, inventory normally returned a skew of approximately `3 ms`, so the checkout continued to payment.

For `eu-west`, inventory normally returned a skew of approximately `47 ms`.

That was expected for the region, but the order service applied the same `10 ms` threshold to every request.

The application treated normal multi-region behavior as a fulfillment failure.

The complete failing decision was now visible in the trace:

```text
Checkout request
      │
      ▼
region=eu-west
      │
      ▼
Inventory response
replicaSkewMs=47
      │
      ▼
FulfillmentGate threshold
MAX_REPLICA_SKEW_MS=10
      │
      ▼
allowed=false
      │
      ▼
HTTP 409
{"error":"fulfillment_rejected"}
```

Payment was never called because the order service rejected the checkout before reaching that stage.

Without the custom Java span, the trace ended at an opaque business response.

With the custom span, the argument, threshold, and returned decision appeared together in the same request.

# Act 6: Fix the application with Cursor

Once the trace provided an exact failing input and business decision, I returned to the code.

> Patch `FulfillmentGate` so the coherence policy supports the multi-region checkout path. Preserve the stricter local-region behavior, use an appropriate configurable threshold for the remote-region path, and add regression tests for both accepted and rejected decisions.

Cursor opened the Java source and replaced the one-size-fits-all policy with a region-aware policy.

The fix did three things:

- Preserved the stricter threshold for the local-region path.
- Added an appropriate higher threshold for multi-region fulfillment.
- Added tests covering successful and rejected coherence decisions.

The important part was not simply that Cursor generated Java code.

Cursor generated the patch after the observability workflow had established:

- The exact service returning the failure
- The successful inventory response
- The missing payment call
- The request category associated with the error
- The method making the decision
- The method argument
- The returned rejection reason
- The hardcoded threshold responsible for the result

Without that evidence, an AI assistant could easily have recommended:

- Retries
- Longer timeouts
- More CPU or memory
- Network policy changes
- Payment-service changes
- Inventory-service changes

All of those would have addressed the wrong problem.

# Act 7: Rebuild, deploy, and verify

After reviewing the patch, I asked Cursor to deploy it.

> Rebuild and push `wsearle/odishop:order-service`, roll out the updated `order-service` deployment, wait for the new pods to become ready, and then verify checkout behavior for both fulfillment regions.

Cursor rebuilt and pushed:

```text
wsearle/odishop:order-service
```

It then rolled out the updated order service and waited for the deployment to become ready.

After the rollout completed, I generated the same checkout traffic again.

The results changed immediately:

- `us-east` checkouts continued to succeed.
- `eu-west` checkouts now succeeded.
- Inventory remained successful.
- Payment appeared on both checkout paths.
- The elevated HTTP `409` responses disappeared.
- The end-to-end traces completed across all four services.
- Odigos instrumentation remained healthy after the rollout.

The formerly failing trace now looked like this:

```text
api-gateway
    │
    ▼
order-service
    │
    ├── inventory-service
    │
    └── payment-service
```

I finished with the same broad question I had used at the beginning.

> Is my OdiShop app healthy now? Check the workloads, instrumentation state, telemetry flow, checkout outcomes, and downstream trace path.

This time, both sides of application health agreed.

The pods were running, telemetry was flowing, and users could complete checkouts successfully.

# Why the Odigos MCP mattered

Jaeger still provided the trace data.

The difference was that I did not need to make the Jaeger UI my primary troubleshooting workspace.

Cursor coordinated three separate surfaces.

## Odigos MCP

Cursor used the Odigos MCP to:

- Check instrumentation health
- Read source and workload conditions
- Inspect the application service map
- Enable source profiling
- Create header and payload collection rules
- Add custom Java instrumentation

These changes could be applied without modifying and redeploying the application for every diagnostic step.

## Jaeger API

Cursor queried Jaeger through a local port-forward to:

- Find failed traces
- Compare successful and failed requests
- Inspect downstream service calls
- Read the newly enriched span attributes
- Verify the final end-to-end request path

Jaeger was queried separately.

Cursor was not accessing Jaeger natively through the Odigos MCP.

## Application code and Kubernetes

Once the root cause was established, Cursor used the repository and Kubernetes workflow to:

- Inspect `FulfillmentGate`
- Patch the region policy
- Add regression tests
- Rebuild the application image
- Roll out the deployment
- Verify the fix

The overall loop looked like this:

```text
Ask Cursor
      │
      ▼
Read Odigos health and topology
      │
      ▼
Query Jaeger traces
      │
      ▼
Add dynamic instrumentation
      │
      ▼
Profile and instrument one method
      │
      ▼
Find the root cause
      │
      ▼
Patch the code
      │
      ▼
Redeploy and verify
```

# Three takeaways

## Application health is more than pod health

Running pods and flowing telemetry prove that the platform is operating.

They do not prove that a business transaction is working correctly.

A useful health check needs both infrastructure state and request-level outcomes.

## Dynamic instrumentation turns generic traces into business evidence

The original HTTP spans identified the failing service.

Header and payload rules identified the affected request category.

Profiling narrowed the search to a Java class.

Custom method instrumentation exposed the exact input and decision.

Each step added only the evidence needed for the next step.

## AI assistants work best when observability constrains the answer

Cursor did not guess the root cause from an opaque `409`.

Odigos and Jaeger provided the evidence, and Cursor used that evidence to move from the cluster, to the trace, to one application method, and finally to the correct code change.

The assistant did not replace observability.

Observability prevented the assistant from fixing the wrong thing.
